## 1. StickS3 하드웨어 대조

SDK 의 `components/muse/boards/board_m5stack_sticks3.c` 와 `devices/sdkconfig.muse-m5stack-sticks3` 를 우리 `docs/sticks3-hardware.md` 와 한 줄씩 맞춰 봤다. 그 파일 머리 주석에는 「핀은 M5 K150 회로도 v0.6, PMIC 비트는 UiFlow2 에서 되읽음」이라고 적혀 있다 [근거: SDK 보드 파일 17~24행].

### 일치 (바꿀 것 없음) [근거: SDK 보드 파일 46~83행]

- I2S: MCLK 18 / BCLK 17 / WS 15 / DOUT 14 / DIN 16
- 내부 I2C: SDA 47 / SCL 48. PMIC 는 0x6E, ES8311 은 기본 주소
- LCD: ST7789, SPI 40 MHz, SCLK 40 / MOSI 39 / CS 41 / DC 45 / RST 21 / 백라이트 38(PWM), 색 반전, 오프셋 x52 y40
- 버튼: KEY1 = GPIO11(정면, 말하기), KEY2 = GPIO12(옆). 둘 다 active-low
- 앰프 enable = PMIC G3, LCD 전원 = PMIC G2(L3B)
- 충전 표시 = PMIC 입력 G0, 충전 중 Low
- 플래시 8 MB, PSRAM 8 MB

### 고친 것 (`docs/sticks3-hardware.md` 에 *2026-10-07 정정* 으로 표시)

| # | 우리가 적었던 것 | 실제 | 근거 |
|---|---|---|---|
| 1 | L3B(PMIC G2) = LCD 전원 | **LCD 와 오디오(코덱) 전원 둘 다.** 코덱을 I2C 에 잇는 선이기도 하다. 끄면 코덱이 버스에서 사라진다 [추론] | SDK 보드 파일 20~21행, 78행 |
| 2 | 앰프: 「0x13 bit3 = push-pull」 | 0x13 은 **1 이 open-drain(PMIC 기본값)**, 0 이 push-pull. enable 선에 풀다운이 있어 open-drain 으로 두면 소리가 안 난다. 그래서 0 으로 내려야 한다 | SDK 보드 파일 77행·170~175행, M5U `bitOff(…0x13…)` |
| 3 | 배터리 전압 0x22/0x23 「12bit」 | **16bit 리틀엔디언 mV.** 0x24/0x25 는 USB 입력 전압 | SDK 81~82행, M5U `getBatteryVoltage` |
| 4 | PSRAM Octal 은 [추론] | Octal 80 MHz 로 [근거] 승격. 32 kHz 크리스털이 없다는 것도 새로 적었다 | `sdkconfig.muse-m5stack-sticks3` |
| 5 | 사용자 LED 미확인, Grove 5V 는 포럼 [추론] | PMIC 0x06 bit4 = 녹색 LED, 기본으로 켜져 1 mA 남짓 먹는다. 0x06 bit3 = Grove·IR 5V | SDK 71~73행·180~182행 |

### 새로 알게 된 것 (문서에 추가)

- **PMIC 상태는 ESP 리셋을 넘어 남는다.** UiFlow2 를 막 지운 기기는 우리 초기화가 틀려도 소리가 난다. 고장은 PMIC 까지 완전히 꺼졌다 켜진 뒤에야 드러난다 [근거: SDK 보드 파일 173~174행]. → **앰프 시험은 전원 버튼 두 번(완전 끄기) 후에 한다** [추론]
- **PMIC 는 작은 MCU 라 I2C 를 가끔 놓친다.** SDK 는 읽기·쓰기를 3회까지 다시 한다 [근거: 90~108행]
- **첫 플래시가 까다롭다.** 출하 UiFlow2 는 ESP32-S3 의 USB 시리얼을 꺼 둔다. BOOT(GPIO0)는 PMIC 가 쥐고 있어 BOOT 버튼도 없다. SDK 문서는 UiFlow2 REPL 에서 USB 시리얼을 되살리는 방법을 쓴다 [근거: `devices/README.md` 134~164행]. 반면 M5 공식 문서는 「전원 버튼 길게 = 다운로드 모드」라고 한다 [근거: docs.m5stack.com StickS3]. 둘 중 무엇이 되는지는 **미확인**. 어느 쪽이든 굽기 전에 8 MB 전체를 백업한다
- **마이크 게인 설정이 M5Unified 와 Muse 가 다르다.** M5Unified 는 아날로그 PGA 를 최소(0x14=0x10)로 두고 디지털 볼륨을 최대(0x17=0xFF)로 올린다 [근거: M5U `_microphone_enabled_cb_sticks3`]. Muse 는 아날로그 입력 게인 30 dB 가 기본이다 [근거: `components/muse/muse_settings.c` 50행]. 아날로그로 키우는 쪽이 잡음이 적을 것 같다 [추론]. 그래서 펌웨어에 `MIC_PGA_DB` 를 넣고 §4 에서 A/B 한다
- **전이중이 된다.** M5Unified 는 스피커·마이크를 I2S 포트 둘에 나눠 번갈아 쓰지만, SDK 는 포트 하나에 TX·RX 를 같이 열고 ES8311 을 양방향으로 쓴다 [근거: 보드 파일 305~350행]
- **초기화 순서**: SDK 는 I2S 를 먼저 켜 MCLK 를 돌린 다음 코덱을 붙인다 [근거: 323~342행]. 커뮤니티 ESPHome 설정의 「클럭이 돈 뒤 ADC 재무장」과 같은 방향이다
- **딥슬립 깨우기**: 두 버튼을 ext1 ANY_LOW 로 건다. 버튼 풀업이 딥슬립 중에도 살아 있다 [근거: 381~400행]

## 2. 우리가 배울 설계

Muse 쪽 흐름 [근거: `components/muse/muse_chat.h` 26~45행, `muse_chat_session.cpp` 16~41행]: 버튼을 누르고 있는 동안 마이크를 **24 kHz PCM16 으로 클라우드 받아쓰기에 흘려 보낸다.** 떼면 받아쓴 글을 채팅으로 보내고, 답은 **글로** 받아 읽는 속도에 맞춰 화면에 넘긴다. 소리로 답하는 부분은 비워 두고 「여기에 각자 TTS 를 붙이라」고 적어 두었다 [근거: `muse_chat_session.cpp` 1512~1530행].

| 항목 | Muse 가 하는 것 | 우리 적용 | 이유 |
|---|---|---|---|
| 업로드 시점 | 누르는 동안 흘려 보냄. 뗄 때쯤 받아쓰기가 거의 끝나 있다 [근거: muse_voice.c 241~248행] | **v1 안 함.** v2 는 P2 후보 | whisper.cpp 는 통째로 받아 적는다. LAN 업로드는 0.2~0.5초로 본다 [추론]. 지연의 대부분은 오클 턴(5~30초)이다(`v1-home-design.md` §5). 흘려 보내 봐야 줄어드는 몫이 작다 |
| 미리 듣기(pre-roll) | 대기 중에도 마이크를 돌려 누르기 전 320 ms 를 고리 버퍼에 둔다. 사람은 누르면서 말을 시작하기 때문이다 [근거: muse_voice.c 47~51행·77~80행] | **P2, 측정 뒤** | 대기 중 코덱·I2S 를 켜 두면 전력이 든다. 첫 음절이 실제로 잘리는지(§4 「첫 음절 잘림률」)부터 잰다 |

## 3. 우리 전용 펌웨어: 방향과 개선 목록

### 추천: Arduino + M5Unified 유지 [추론]

근거
1. **지연의 대부분은 펌웨어 밖에 있다.** 오클 턴 5~30초에 비하면, 펌웨어를 고쳐서 줄일 수 있는 몫은 1초 안쪽이다(`v1-home-design.md` §5). 언어를 바꿔서 얻을 게 적다
2. **M5Unified 가 PMIC·앰프·코덱을 이미 처리한다** [근거: M5U StickS3 분기]. 필요한 몇 개만 `M5.In_I2C` 로 직접 쓰면 된다. 이번에 쓴 `bitOn/bitOff/readRegister/writeRegister8` 은 M5U `I2C_Class.hpp` 에 있는 함수다 [근거]
3. Arduino-ESP32 3.x 는 ESP-IDF 위에 올라가 있다. 그래서 `esp_sleep_*` 같은 IDF API 를 그대로 부를 수 있다 [추론]. 펌웨어 하나에 300줄 남짓이다
4. ESP-IDF 로 옮기면 할 일이 많다. 보드 초기화, LCD, 코덱, 버튼을 우리가 다 다시 써야 한다(SDK 는 베끼지 않는다). Muse 의 StickS3 보드 파일만 435줄이다

**ESP-IDF 로 갈 조건** (하나라도 걸리면 그때 다시 정한다)
- 배터리 대기 시간이 목표(하루) 밑이고, 원인이 라이트슬립·전원 관리 설정을 못 쓰는 데 있을 때
- 전이중 끼어들기나 에코 제거가 필요해질 때(M5Unified 는 포트 둘을 번갈아 쓴다)
- v2 에서 녹음 중 흘려 보내기와 압축이 필요하고, Arduino `HTTPClient` 로는 청크 전송·되밀림 처리가 안 될 때
- 서명·롤백이 있는 OTA 가 필요할 때

## 4. 벤치마크 계획 (도착 후)

### 4-0. Muse 펌웨어를 비교용으로 돌릴 수 있나

| 조건 | 사실 | 등급 |
|---|---|---|
| 말→답 한 바퀴 | Muse 계정, 그 계정에서 받은 **SDK 토큰**(gadgets.muse.ai), 휴대폰 Muse 앱의 개발자 모드 페어링이 모두 필요하다 | [근거: SDK `README.md`, `esp32/README.md`] |
| 한국에서 계정 | Meta 공식 발표는 「미국에서 iOS·Android·muse.ai 로 출시」뿐이다. 그 밖의 나라는 「아직 이용할 수 없음」이라는 제3자 보도가 있다 | 출시 지역은 [근거: about.fb.com/news/2026/09/introducing-muse-personal-ai-agent], 한국 불가는 [근거: 제3자 usecarly.com, zentor.ai] |

| 답의 형태 | 기기에는 **글로만** 답한다. 소리 답은 각자 TTS 를 붙이라고 비워 뒀다 | [근거: muse_chat_session.cpp 머리 주석 16~41행 중 3단계, 1512~1530행] |
| 약관 | 개인·비상업, **자기 계정**으로만. 50대 한도. 사용 제한·안전장치를 우회하면 안 된다. 벤치마크를 따로 막는 조항은 없다 | [근거: 약관] |
| 약관 위 상위 약관 | Muse Supplemental Terms (muse.ai/terms) | **읽지 않음** |

**결론**
- **Muse 펌웨어로 말→답 한 바퀴를 비교하는 건 이 집에서는 불가능하다.** 계정이 나라 단위로 막혀 있다. 우회는 약관의 「사용 제한 우회 금지」에 걸릴 수 있다 [추론]. 하지 않는다.
- 설령 돌아가도 기기에서 나오는 건 글뿐이다. 그래서 「첫 소리까지」는 처음부터 비교할 수 없다. 견줄 수 있는 건 「첫 글자까지」다.
- 계정 없이 굽고 켜서 쓸 수 있는 건 **하드웨어·전력 기준점**이다. 화면 끈 대기 전류, 라이트슬립 전류, 딥슬립 전류, 설정 화면의 마이크 레벨, 버튼 반응. 이건 [추론]이고 실기에서 확인해야 한다.
- Muse 를 굽으려면 ESP-IDF 6.0.1 과 `brew install cmake ninja dfu-util` 가 필요하다 [근거: SDK `esp32/README.md`]. 전역 설치라 **따로 승인을 받는다.** 굽기 전에 출하 펌웨어 8 MB 를 백업한다.

### 4-2. 측정 항목과 방법

**A. 단계별 응답 지연** (O 만, 20회)
- 단계: 누름 → (녹음) → 뗌 → 업로드 시작 `post` → 서버 응답 헤더 `hdr` → 본문 다 받음 `body` → 재생 시작 `play`. 서버 쪽 `stt / llm / tts` ms 는 `X-Timing` 에서 온다.
- 기기 시계: 시리얼 `timing ms:` 줄(뗀 순간 = 0). 서버 시계: sqlite `requests` 표.
- **바깥 시계**(기기 시계를 믿지 않기 위해): 휴대폰을 기기 옆에 두고 녹음한다. 버튼 딸깍 소리부터 답 첫 소리까지를 파형에서 잰다. 기기 줄과 30 ms 넘게 어긋나면 기기 계측을 의심한다.
- 질의 세트: 짧은 사실 질문 10개(「지금 몇 시야」 류) + 집 기기 조작 10개. 오클 턴이 질의마다 다르므로 **같은 문장을 같은 순서로** 쓴다.
- 보고: 단계마다 중앙값과 최대값. 평균만 쓰지 않는다(이상치 정지를 가린다).
- M-hw 와는 비교하지 않는다(답이 안 온다).

**B. 한국어 인식률** (O 대 O-pga)
- 스크립트 20문장(숫자·고유명사·기기 이름 포함) × 2 거리(30 cm, 1 m) × 2 환경(조용, TV 소리) × 2 회.
- `BENCH_DIR` 로 기기가 보낸 WAV 를 그대로 남기고, `LOG_TEXT=1` 은 벤치마크 동안만 켠다.
- 지표: 글자 오류율(CER). 정답 원문과 STT 결과를 공백을 빼고 편집거리로 계산한다.
- 대조군: 같은 문장을 맥미니 내장 마이크로 녹음해 같은 whisper 에 넣는다. 「마이크 탓」과 「STT 탓」을 가른다.
- **첫 음절 잘림률**: 누르면서 바로 말한 경우만 따로 센다. 5% 를 넘으면 P2 미리 듣기를 넣는다.

**C. 음질**
- 마이크: 우리 코드로 루프백을 짠다(스피커 −12 dBFS 음 → 마이크). 잡음 바닥(dBFS), 1 kHz 레벨, 잘림 여부를 `MIC_PGA_DB` = −1/12/24/30 에서 잰다. M-hw 설정 화면의 마이크 미터와도 맞춰 본다.
- 스피커: 같은 TTS 문장 5개를 30 cm 에서 휴대폰 소음계 앱으로 최대 dB 를 잰다. 사용자가 1~5점으로 매긴다(알아듣기 쉬움). `say` 목소리 후보(Yuna 등)를 같이 비교한다.

**D. 배터리 지속**
- 완충 → 꺼질 때까지 시간. 세 가지 조건: (1) 화면 켠 대기, (2) 우리 기본값(20초 뒤 어둡게, 5분 뒤 딥슬립), (3) 5분마다 질의 1회.
- 기록: 테스트용으로 1분마다 배터리 mV 를 서버에 보내는 빌드를 따로 만든다(본 펌웨어에는 넣지 않는다). 배터리 % 는 펌웨어마다 계산식이 달라서 쓰지 않고 **mV 로만** 비교한다.

**E. 대기 전류**
- 도구: USB-C 인라인 전류계. 지금 없으니 **구입 결정이 필요하다.** 정밀하게 재려면 Nordic PPK2 같은 전원 분석기가 낫다.
- 한계: USB 로 재면 충전 전류가 섞인다. 완충 상태에서 재거나 배터리 끝 단자에서 재야 하는데, 이건 분해가 필요할 수 있다 [추론].
- 조건별(O / M-hw / F): 화면 켬, 화면 끔+Wi-Fi 연결, 딥슬립, PMIC 전원 끔(두 번 누름). 각 5분 평균.

### 4-3. 공정 비교 조건

- 같은 기기 한 대로 펌웨어만 바꾼다. 두 대 비교는 기기 편차를 따로 잰 뒤에만.
- 같은 공유기, 같은 위치(공유기와 3 m). 측정 전에 RSSI 를 적는다.
- 음량은 같은 dB 가 나오게 맞춘 뒤 잰다.
- 측정 순서를 펌웨어마다 번갈아 바꾼다(O → M-hw → O …). 배터리 노화와 온도 영향을 섞는다.
- 모든 원자료(시리얼 로그, sqlite, WAV, 휴대폰 녹음)를 날짜 폴더에 남긴다. 「통과」만 적지 않는다.
